# AI 辅助映射自扩展——目标与方法论（定稿）

> 更新：2026-08-24
> 定位：把"AI 辅助映射自扩展"这件事的目标、内核边界、验证标准钉死，防止目标漂移和过拟合。

---

## 一、目标（两个层次，分清楚）

### 目标 1：原项目交付 —— IOA 采集能力验证
- 产出：能力矩阵 + 字段映射 + 三态 verdict（对 / 错 / 疑问）
- 状态：21 已定稿 + 15 待定稿 + 17 预留
- 性质：**交付物**，服务于"验证 IOA"这个具体场景。

### 目标 2：方法论验证 —— AI 辅助映射自扩展可复用
- **核心命题**：*「自动建 oracle + 自动映射发现」是可复用、可复现的方法，既不依赖某个特定观测系统（IOA），也不依赖某个 AI 对话的历史上下文。*
- **验证标准（范式 B）**：一个**零历史的新上下文**，只读"抽离的内核文件 + 工具 + 规则"，能对一个**新模块 / 新观测系统**独立完成映射，且人工介入量显著低于纯手工。
- **明确排除范式 A**：靠当前对话的历史记忆补映射（那只是效率加速器，不是方法论验证的证据，本质是过拟合到上下文）。

> 一句话：目标 1 证明"IOA 采没采到"；目标 2 证明"这套方法换谁、换哪都能用"。

## 二、内核 vs 适配层（防过拟合的分界线）

| 内核（通用，保住） | 适配层（特化，可插拔） |
|---|---|
| 三层 ground truth（L0 声明 / L1 回读事实 / L2 独立参照）| IOA 日志解析器（normalizer）|
| 正向值扫描：已知值 → 日志找落点 | 字段名映射（ioa_field_mapping.json）|
| 反向剖析：日志有值字段 → 反推补什么 | 锚点策略（MD5 + 时间窗）|
| 映射生成：behavior_fields + observed_fields | 冻结协议 stdout 具体格式 |
| 可扩展机制：加 case 自动补映射 | 具体 case 定义 |

**过拟合判断标准（一条）**：把 IOA 换成 Sysmon，内核逻辑一行不动、只换适配层，还能跑通 → 没过拟合。

---

## 三、抽离的"内核文件"应包含什么（范式 B 的输入）

验证时，新上下文**只准读**这份内核文件 + 工具 + 规则：

1. 三层 ground truth 方法论（声明 / 事实 / 独立参照）；
2. 双向映射发现的通用流程（正向值扫描 + 反向剖析交替）；
3. 映射产物结构（通用字段：已知值 → 落点、观测到的业务字段清单）；
4. 可扩展机制（新增行为如何自动补映射）；
5. 锚点 / 判定的**通用原则**（用稳定标识 + 时间容差，而不是"MD5+时间窗"这种 IOA 特化）。

**内核文件不含**：IOA 字段名（如 Child.FileMd5）、具体 case（如 FILE-CREATE-001）、冻结协议的具体格式。

## 四、污染问题的边界（回答"同文件夹会不会污染"）

- **物理上放同一个文件夹：OK**——这是同一个项目，本该放一起。
- **真正要隔离的是逻辑层**：内核逻辑 vs IOA 特化逻辑，不能写死在同一个函数 / 同一份文档里。
- **验证时**：只喂内核文件，不"偷看" IOA 的字段名、锚点、具体 case——否则就是假验证。

---

## 五、验证实验设计

1. **Sysmon 对照**：同一个样本，对 Sysmon（第二观测系统）也跑一遍映射自扩展，证明内核可迁移；
2. **零历史补映射**：开一个新对话，只喂内核文件 + 一个新模块（如 Hash / Service）的 stdout + 日志，看能否独立补出映射；
3. **量化指标**：AI 自动发现的映射 / 人工定稿的映射（覆盖率），以及人工介入的次数。

## 七、样本生成思路复用（L0/L1 层）

> 补充：不仅「字段映射方法」可复用，「样本生成思路」也可复用。

| 可复用（通用） | 特化（适配层） |
|---|---|
| 标准触发方式（一个行为的标准触发，如计划任务 = schtasks+XML）| 针对 IOA 的触发调整 |
| 冻结协议 stdout（确定性值 + 自证）| 冻结协议的具体字段格式 |
| 自清理 / Migration gate 7 条 | 具体 case 定义 |

**L2 的真正用法**：Sysmon 用来「验证样本本身」——独立确认样本确实触发了目标行为，而不是只信样本自述。这是「样本可复用」的前提。

**难点**：「样本不是部分情况触发采集能力」很难衡量 → 本质是「行为定义」问题：一个行为有多种触发方式，IOA 对每种方式的采集可能不同。「标准触发方式」没有绝对标准，只有约定。

**解法**：建「行为定义清单」，约定每个行为的标准触发方式（参考 EDR-Telemetry 的 category 定义），把「部分情况」从玄学变成有据可依。

## 八、L2 落地实录（Sysmon 独立参照已跑通）

> 2026-08-24 落地，全链路验证通过。

- **落地方式**：每个 case 跑完自动导出 Sysmon evtx（`sysmon_<case>.evtx`），与 IOA 云端 JSON 平行对照；
- **验证证据**：样本进程 ID1（`Image=...\FileLifecycleTest.exe`）+ 行为 ID11（`Target=...FileLifecycle_Target.exe`）均被 Sysmon 独立记录；
- **结论**：**L2 从概念变成可用事实**——样本行为在 Sysmon 侧有独立证据，可作字段映射 / 采集判定的平行参照。

**提炼的方法论认知**：独立参照必须「隔离」——Sysmon 装在单独快照（IOA_Sysmon），与纯 IOA 快照区分，避免参照污染被测系统。（工程细节：case 级 `snapshot` 字段优先级高于 `vm_config`，见交接文档。）

## 九、收紧样本行为的两个方式（边界要分清）

> 目的：让样本行为「标准、可信」，避免「碰巧触发部分情况」。

### 方式 1：EDR 反哺（收紧「触发方式」）✅ 允许

用 EDR「采没采到」的结果，诊断样本的**触发方式**是否标准，并调整样本（如计划任务 COM→schtasks+XML）。

**边界（红线）**：只能反哺「触发方式 / 行为定义」，**禁止**用 EDR 日志里的字段值（如 `FileTotalWrite=0`）定义样本的锚点/期望值——锚点必须来自 L1 样本自报，否则是循环论证（用 EDR 输出验证 EDR）。

### 方式 2：Sysmon 验证（收紧「行为确实发生」）✅ 允许

用 Sysmon 独立确认样本确实触发了目标行为（L2 参照），避免只信样本自述。

### 方式 3：制作行业规范样本（每个 case 都要做）✅ 必须

每个行为除「EDR 反哺后的收紧样本」外，还要备份一份**行业规范样本**——对照 EDR-Telemetry category 定义的标准触发方式，不做任何针对 IOA 的调整。

- **目标文件类型：有内容的 .exe（方案 A，已定稿）**。理由：.txt 是 IOA 和 Sysmon 的采集盲区（IOA 只采 DLL/EXE/PS1/JS/SYS/XML/PNG 的删除；SwiftOnSecurity 默认配置不含 .txt 的 FileCreate/FileDelete），用 .txt 测出的「未采集」说服力会被削弱。
- **行业规范样本标准**：标准触发方式 + 正常行为（创建就正常写内容、删除就正常删、不 sleep、不迁就传感器合并窗口）+ 确定性锚点值（全部 L1 自报，绝不抄 EDR）。
- **与收紧样本的关系**：收紧样本解决「能不能被 IOA 采到」，行业规范样本解决「行为本身是否标准」——两个版本并存，各留 MD5 与源码版本记录。

## 十、全局执行指令（每个行为必须遵守）

1. **每个行为（case / 模块）做完必做「备份记录」**：记录做了什么、结论（三态）、遗留问题、依赖的样本版本 / 日志时间窗。落点：样本侧 → `docs/<MODULE>_SAMPLE_AUDIT.md`；映射侧 → `docs/<MODULE>_MODULE.md`。
2. **自动化链路每增长一步，记录在案**：链路新增环节（如 EDR 反哺、Sysmon 验证、行业对比）时，更新 `docs/AI_CHAIN_LOG.md` 的链路拆解 + changelog。
3. **有问题实时更新，不改历史**：发现日志有问题 / 结论要改，追加到对应记录文档，标注「更新日期 + 原因」，不覆盖旧记录（留痕）。
4. **每个 case 必做两件事**：① 收紧样本（EDR 反哺触发方式 + Sysmon 验证行为确实发生）② 制作行业规范样本（备份 + 记录）。两个版本都落盘 + 记录 MD5 / 源码版本，缺一不可。
