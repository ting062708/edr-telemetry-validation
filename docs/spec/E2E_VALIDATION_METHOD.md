# 端到端验证方法（E2E Validation Method）

> 定位：围绕 EDR 完成**产品数据采集能力验证与 BASELINE 构建**的核心方法。
> 一条样本从"制作"到"判定 IOA 采集能力"的完整端到端链路。
> 更新：2026-08-24

---

## 一、端到端流程（四步）

```
① 样本制作（行业规范）
        ↓
② Sysmon 命中验证（样本有效性）← 不命中则收敛样本，回 ①
        ↓
③ 拿样本当 case 跑测试
        ↓
④ 对比日志 + Sysmon 收敛样本 → 判定 IOA 采集能力
```

### 步骤①：样本制作（按行业规范）

- **触发方式对齐标准**：参照 `docs/EDR_TELEMETRY_BASELINE.md`（EDR-Telemetry category 定义），用「标准触发方式」触发目标行为（如计划任务 = `schtasks + XML`，而非 COM API）；
- **冻结协议 stdout**：遵循 `docs/STDOUT_SPEC.md`，只补「样本确定知道 + IOA 原样记录」的字符串值；
- **自清理 + 去重规避**：样本自清理残留，涉及「建删」类的行为要 `sleep` 拉开间隔（如 Account 的 lsass 异步去重需 `sleep 5s`）；
- **Migration gate 7 条**：遵循 `SAMPLE_INVENTORY.md`。

### 步骤②：Sysmon 命中验证（样本有效性，端到端第一步）

- 跑样本，看 **Sysmon（L2 独立参照）** 是否真正记录了该行为；
- **命中** → 样本有效，进入步骤③；
- **不命中** → 收敛样本（调整触发方式），回到步骤①；
- **交替三次不命中** → 判定「样本失败」，记录后转下一个行为（对齐全局提示词：自优化上限 3 次）。

### 步骤③：拿样本当 case 跑测试

- 样本投递 IOA 环境，`run --case <CASE-ID>` 跑；
- 导出 IOA 日志（**注意控制台筛查条件要选对**，否则误以为无日志）；
- 日志放 `log\<模块大写>\json\`。

### 步骤④：对比日志 + Sysmon 收敛样本 → 判定采集能力

- 对比 **IOA 日志** vs **Sysmon 日志**，按下方判定矩阵定结论；
- 结论落三态 verdict（对/疑问/错）+ 记录缺失及异常采集问题。

## 二、判定矩阵（能力维度 × 锚定维度 × Sysmon）

> **核心原则（2026-08-24 修正）**：「采集能力」的判定标准是 **IOA 有没有这个行为类型事件的能力**，
> 而不是「IOA 有没有采到我这个特定测试进程」。能力看事件类型，锚定看样本进程，两者正交。

| 能力（IOA 有该行为类型事件） | 锚定（IOA 采到样本进程） | Sysmon | 结论 | 动作 |
|---|---|---|---|---|
| ✅ 存在 | ✅ 锚定 | ✅ | **采集能力存在 + 样本被采** | 判「对」，定稿 |
| ✅ 存在 | ❌ 未锚定 | ✅ | **采集能力存在，但样本进程被过滤** | 判「对」+ 记「异常采集现象」（进程信任过滤 / 路径排除 / cmd 包装 / 待验证）|
| ❌ 不存在 | ❌ | ✅ | **采集能力缺失（IOA 能力缺口）** | 判「错」，记录缺失 |
| — | — | ❌ | **样本触发问题** | 收敛样本，回步骤① |
| ✅ 存在 | ✅ | ❌ | **异常**（IOA 采到、参照没采到）| 排查 Sysmon 配置，记录异常 |

### 匹配流水线与时间窗取值规则（2026-08-26 补）

日志处理分两条**正交**判断线，别混为一谈：

**线 1 —— 锚定线（判定「样本进程是否被采」）**，顺序固定、层层收窄（对应 `core/matcher.py`）：

```
Hostname → 时间窗（RUN区间 ± slack）→ Actor 进程名 → PID → MD5 精确锚定 → Operation → 额外字段
```

- 时间窗是第一道粗筛：不先收窄，直接按进程名/MD5 在全量日志里匹配，会被其它时间段的同类事件干扰、锚错对象。
- 时间窗优先用 **RUN 区间**（`RUN-BEGIN..RUN-END`，覆盖 SETUP+TARGET+验证整段），因为账户创建等行为常发生在 SETUP 阶段、不在 TARGET 瞬间；RUN 缺失时才回退到 TARGET 区间。
- `slack`（加减范围）默认 `pre=5s / post=30s`（post 放宽以等云端延迟入库）；可在 `test_cases.json` 用 `match.pre_slack_s / post_slack_s` 按 case 覆盖；**fullcycle 多阶段样本默认收紧到 3s**（阶段间隔仅 5-7s，30s 的 post 会把相邻阶段同类事件吞进来）。
- 时间过滤会丢弃无时间戳（`event_time_utc=None`）的事件，属预期。

**线 2 —— 能力线（判定「IOA 是否有该行为类型的事件」）**，在**全量日志**上找 `operation`（+可选 `capability_probe` 精确字段）是否存在，**不过时间窗、不看进程**（`matcher.py` capability 段遍历全部 `events`）。

- 为什么不能套时间窗：能力是产品属性，与「这次样本跑没跑、日志覆盖没覆盖该时段」无关；套了时间窗，日志没覆盖到运行时刻就会误判成「能力缺失」。

两条线的产出分别落 `match_result.json` 的 `capability_detected`（能力，主结论）与 `anchor_detected`（锚定，辅助证据），见下一小节。

### 两个维度的落地字段（match_result.json）

- **capability_detected**：日志里存在该行为类型事件（operation + 可选 capability_probe 精确字段）→ `true/false`。
  这是 **verdict 的主结论**。
  - 注意粒度：`FileWriteClose` 一个事件类型覆盖「新建/覆盖写/打开」三个行为，
    必须靠 `capability_probe.field`（如 `Child.FileCreateOpName`）精确到行为，不能只看 Action.Name。
- **anchor_detected**：是否锚定到样本进程（actor/PID/MD5）→ `true/false`。这是**辅助证据**。
- **anomaly**：`capability_detected=true` 但 `anchor_detected=false` 时，记录异常采集现象根因。

### 验证根因（当 anomaly 出现时）

「样本进程没被采」不等于「能力缺失」。先区分三个候选根因：
1. **路径排除**：`C:\EDRTest` 被加进排除列表 → 把样本改写到 `C:\Users\tester\Desktop\` 重跑，能采到即为路径排除；
2. **进程信任过滤**：未签名进程的文件活动被过滤 → 换路径仍采不到即坐实；
3. **cmd 包装**：样本被 cmd.exe 启动，IOA 不跟子进程链的文件操作。

> Sysmon 是「事实裁判」：它采到了而 IOA 没采到，才能证明是 IOA 的缺口；如果 Sysmon 也没采到，那多半是样本没真正触发行为。

## 三、产出（对应项目目标）

| 产出 | 说明 |
|---|---|
| **数据采集测试样本** | 经过 Sysmon 命中验证的有效样本（行业规范 + 冻结协议）|
| **端到端 BASELINE** | 三态 verdict 矩阵 + 缺失/异常采集记录 |
| **自动化对比脚本** | 样本批量测试 + 结果与 BASELINE 自动对比输出结论 |

## 四、与 AI 工程文档的关系

- 本方法是**原项目主流程**（不涉及 AI 辅助）；
- AI 辅助落在流程各环节的效率提升上，对应 `docs/AI_ENGINE.md` 的 4 个行为链：
  - 步骤①② → 行为链①样本构建；
  - 步骤③ → 行为链②跑样本；
  - 步骤④ → 行为链③找映射 + 行为链④结论分析。
