> 一句话：用例级三态 + 能力级并集判定 + 行业对比 + AI 行为结果分析（可循环反哺样本构建）。

## 一、自动化实现（现状）

- 三态判定：`config/case_result_map.json`（对 / 疑问 / 错）+ `status.py` 的 `_verdict_to_binary` 前端四色；
- 行业对比：`config/industry_baseline.json`（53 category × Sysmon/MDE/CrowdStrike/SentinelOne）+ summary 行业对比列；
- AI 行为结果分析：`result_analysis` 字段（预留，规范见 `AI_SUMMARY_SPEC.md`）——采到/漏采/根因/行业/建议；
- 前端展示：summary.html（表格：行为 / 判定 / 结论 / 行业对比 / AI 分析占位）。

## 二、目前规则

- 三态：对（完整采集）/ 疑问（部分采集）/ 错（无采集），导师标准"部分=通过"；
- 行业对比 4 标签：🟢行业对齐 / 🔴能力缺口 / ⚪行业常态缺口 / ⭐领先行业；
- **反哺**：结论分析发现样本问题（如触发方式不对）→ 回行为链 ① 重构样本（循环，不是单向）。

### 能力级判定（多用例确认采集能力）

> 背景：EDR 采集存在**偏向性**——同一能力（capability）的不同触发方式，EDR 可能只覆盖其中一部分。单个用例"没采到"不能直接判定"无采集能力"，可能只是这个触发方式恰好不在 EDR 采集范围内。

- **两个层级要分清**：
  - **用例级**：单个 case 的三态（对/疑问/错），反映"这个触发方式有没有被采到"；
  - **能力级**：一个 capability 是否具备采集能力，需**多个触发方式的用例**共同确认。
- **能力级判定用并集**：一个能力准备 N 个不同触发方式的用例，判定规则——
  - 任一触发方式被采到 → **能力存在**（对）；
  - 部分触发方式被采到 → **采集有偏向**（疑问，仅覆盖部分触发路径）；
  - 全部触发方式都触发了、但都没被采到 → **能力缺失 / 采集盲区**（错）。
- **关键前提**：每个用例必须先用 Sysmon（L2）独立验证"行为确实发生"，才能把"IOA 没采到"归因于 EDR 能力，而非"样本根本没触发"。
- **落地**：样本命名 `<模块>-<能力>-<序号>` 为"一能力多用例"留扩展位；每个能力在 `BEHAVIOR_LEDGER` 约定标准触发方式清单。
